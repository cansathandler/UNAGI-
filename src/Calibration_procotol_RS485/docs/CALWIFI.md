# 校正用 WiFi ビルド（env:node_calwifi）

ノード1台を治具に載せ、**電源は XT30 だけ**、PC とは **WiFi** で直接つないで `hall_calib_gui.py` を使うためのビルドです。ヘッドも RS-485 も USB もいりません。

## 本番ビルドへの影響

- 追加したコードは、すべて `#ifdef UNAGI_CAL_WIFI` の中にあります。
- 本番の `env:node` には WiFi のコードが一切入らず、走行時の動作と RS-485 プロトコルは変わりません。
- 本番用のソースで変わったのは1行だけです。`loop()` の `hall` 表示の条件に `&& !cal_busy` を足しました。本番では `cal_busy` が常に `false` なので、動作は同じです。

## 使い方

1. **書き込み**：USB を挿して、PROJECT TASKS → **`node_calwifi ▸ General ▸ Upload`**。
   - ID・較正値・dir は NVS に残ります（書き換えません）。
   - 起動時に USB モニタへ `CAL WiFi: SSID UNAGI-NODE-<id> / unagi12345 -> 192.168.4.1:5000` と表示されます。
2. **USB を抜き、XT30 から給電**します。
3. **PC（Mac）の WiFi を `UNAGI-NODE-<id>` につなぎます**（パスワード `unagi12345`）。
   - このネットワークはインターネットにつながりません。
   - Continuity Camera が使えなくなる場合は、iPhone を「Phone records itself」モードにするか、iPhone と Mac を USB ケーブルでつないでください。
4. `python hall_calib_gui.py` → タブ1 Motor node で **Wi-Fi**、ホスト **`192.168.4.1:5000`** → Connect。
5. 以降は通常どおりです（START take → タブ2）。
   - コイル漏れ k は、関節をクランプしてからタブ3 の **Measure k now** を押します。
6. **校正が終わったら必ず `node ▸ Upload` で本番ファームに戻してください。**

## コマンド（TCP、1行ずつ。GUI のタブ1の Cmd 欄からも送れます）

| コマンド | 内容 |
|---|---|
| `HALL 1` / `HALL 0` | 1 kHz で `time_us,v1,v2,u_milli` を流す（`STREAM_START` / `STREAM_END` で囲まれます） |
| `WAVE DC\|SINE\|SQUARE\|TRI` | 波形の種類 |
| `AMP` `FREQ` `DUTY` `PHASE` `OFFSET` `LIMIT` | 波形のパラメータ |
| `RUN` / `STOP` | 開ループ駆動の開始と停止。u は dir を掛ける前の値（+u で角度が増える向き）、MIN_DUTY は NVS の値 |
| `RUNMAX <ms>` | RUN の自動停止時間（既定 15000 ms） |
| `STATUS` / `PING` / `HELP` | 状態表示・応答確認・一覧 |

## 安全機能

- 次のどれかが起きたら、必ずモータを止めます。
  - TCP が切れたとき
  - 新しいクライアントが接続したとき
  - nFAULT が 5 ms 以上 Low になったとき
  - RUNMAX を過ぎたとき
- ヘッドから走行（WAIT / RUN）が来た場合は、校正の駆動とストリームを止めて走行を優先します。

## 検証

- PC 上で、Arduino / FreeRTOS / WiFi の代替実装を使ってファームを動かし、GUI の通信コードで接続して確認しました。
  - ストリーミングが 1000 Hz で出ること
  - 同期パルスが +0.6 を 250 ms、−0.6 を 250 ms 出すこと
  - RUNMAX で自動停止すること
  - 切断で停止すること
  - k が正しく求まること（シミュレーションの真値 40 に対して 39.95）
- 本番ビルドと校正ビルドの両方が、警告なしでコンパイルできることも確認しました。
- **ESP32 実機用のツールチェーンでのビルドは、まだ確認していません。** 最初の書き込みのときに、ビルドが通るか確認してください。

# 角度の計算式の変更（v1+v2 − k·u）— 本番 `node` と校正 `node_calwifi` の両方に入っています

## 変更の理由

モータ10の実測で、S1 と S2 が角度に対して**同じ向き**に動くことがわかりました。そのため、従来の v1−v2 では角度の信号が打ち消されてしまいます。v1+v2（和）なら角度の校正誤差は 0.37° RMS ですが、コイルの漏れ磁場（u が 1 あたり約 −130 カウント）が上乗せされるので、それを補正します。

## 本番ファームの角度の式

```
s = v1 − v2   (sig = diff, 既定。今までと同じ)
s = v1 + v2   (sig = sum)
d = s − k · u_applied        u_applied = 直前に出力した指令（dir を掛ける前、−1..1。待機中は 0）
θ = c0 + c1·d + c2·d² + c3·d³
```

- `sig` と `k` は NVS に保存します（キーは `sig` と `kc`）。**どちらも未設定なら、従来とまったく同じ動作**（v1−v2、k = 0）になります。
- 走行中は START の時点の値を使います（`run_sig`、`run_k`。CAL の扱いと同じです）。
- 1 kHz の制御ループでは、ADC で Hall を読むときに流れている電流が「直前の周期で出力した u」なので、その値で補正します。
- peek・zero・show・hall の表示もすべて同じ式で計算します（待機中なので u = 0）。
- RS-485 のプロトコルは変えていません。`push_cal.py`（c0..c3 の書き込み）もそのまま使えます。

## 設定のしかた

**A. 校正 GUI から（おすすめ）**：ノードが `node_calwifi` の状態で、`hall_calib_gui.py` のタブ2 → **Write CAL to node** を押します。
- c0..c3、sig、k をまとめて NVS に書き込みます。
- ノードの id と Motor # が違う場合は書き込みません。
- 書き込んだあと、値を読み返して確認します。

**B. USB シリアルから**：`sig sum` → `k -130.2` → `cal c0 c1 c2 c3` → `save`。`show` で確認できます。

**C. 校正ファームの TCP コマンド**：`GETCAL` / `SETCAL c0 c1 c2 c3` / `SETSIG diff|sum` / `SETK k` / `SAVE`

## 注意

- **k は、本番と同じ MIN_DUTY と dir の状態で測ってください。** u からコイル電流への換算は MIN_DUTY に依存するので、あとで MIN_DUTY を変えたら k を測り直します。
- **k·u の補正は「電流が u に比例する」ことを前提にしています。** 電源電圧の低下、コイルの温度上昇、電流の立ち上がりの遅れによって、0.5〜1° 程度の誤差が残る可能性があります。
- **確認のしかた：** `joint1` などの閉ループ制御で、カメラの角度とノードがログした角度（meas）を比べてください。
- **検証の範囲：** PC 上で代わりの部品を使って動かし、ビルド（本番・校正の両方で警告なし）、GETCAL/SETCAL/SAVE、id の照合、読み返しを確認しました。GETCAL が、固定した関節の角度 7.00° に対して 7.10° と正しく出ることも確認しています。**本番の走行ループでの補正（ヘッドからの START で走る経路）は、実機で確認してください。**

# ソフトウェア電流制限（ULIM）— 本番 `node` と校正 `node_calwifi` の両方に入っています

- **何をするか：** NVS の `ulim`（0〜1、既定は 1 = 制限なし）で、**すべての駆動で |u| ≤ ULIM** に制限します。対象は、走行中の制御ループ、USB の `pwm`、校正ファームの RUN です。
- k·u の補正とログの u には、**制限後の u** を使います。
- **設定方法（おすすめ）：** `hall_calib_gui.py` のタブ5「Current limit」を使います。
  1. 関節を固定します（止めた状態の電流が最大です）。
  2. 電源を、実際に使う中でいちばん高い電圧にします。
  3. u = 0 のときの電流（アイドル電流）と、各ステップ（Run、自動で停止）の電流を、電源装置の表示から入力します。
  4. Fit → 最大電流から ULIM を計算 → Write ULIM to node。
  - 試験の各ステップは、一時的に ULIM = 1 にして実行し、終わったら元の値に戻します（NVS は変わりません）。
- **USB シリアルから：** `ulim 0.5` → `save`。`show` で確認できます。
- **校正ファームの TCP コマンド：** `SETULIM u` → `SAVE`。`GETCAL` に `ulim=` が表示されます。
- **注意：** 電流は電源電圧に比例します。最大電圧で決めた ULIM なら、それより低い電圧では電流は必ず小さくなります。関節が動いているとき（逆起電力がある）や、コイルが温まっているとき（抵抗が上がる）も、電流は小さくなります。電源装置の電流制限は、二重の安全策として残しておいてください。

# ヘッド経由の校正（RS-485 ブリッジ）— 本番 `head` と本番 `node` に入っています

ヘッドとノードを RS-485 でつないだまま、`hall_calib_gui.py` と `hall_live.py` を**今までと同じ画面で**使えます。ノードを `node_calwifi` に書き換える必要はありません。

ノード単体の WiFi（`node_calwifi`）と比べて、次の点が違います。
- 実際の配線（ヘッド → RS-485 → ノード）のまま測れます。
- ヘッドの INA226 で測った**電源電圧と電流**が、1 kHz の各 Hall サンプルに付きます。

## 書き込み

- **ヘッド：** `head ▸ Upload`（fw `head-v2-rs485-3.1.0`）
- **ノード：** `node ▸ Upload`（fw `00030002`）
- ID・較正値・ULIM などの NVS の値はそのまま残ります。
- **プロトコル番号は 3 のまま**です。ただし、新しいヘッドと古いノードの組み合わせでは校正ブリッジが使えません。両方を書き換えてください。

## 使い方

1. ノード（例：10番）をヘッドにつなぎ、ヘッドに給電します。
   - INA226 の電流は「ヘッドから給電しているノード全部」の合計です。電流を測るときは、**駆動するのは1台だけ**にしてください。ほかのノードがつながっていても、止まっていれば構いません。
2. PC の WiFi を **`UNAGI-HEAD` / `unagi12345`** につなぎます。
3. `hall_calib_gui.py` を開き、タブ1 Motor node で次のように設定して Connect します。
   - 接続方法：**`Head (RS-485)`**
   - ホスト：**`192.168.4.1:5000`**
   - Motor # を、測りたいノードの ID にしておきます。
4. 接続すると、GUI は次の2つを自動で送ります。
   - `NODE <Motor #>`：転送先のノードを選びます。
   - `HEAD POWER 1`：ヘッドのロードスイッチを入れ、ノードに給電します。
   - 「Head: Power ON / OFF」のボタンでも給電を切り替えられます。
5. あとは今までと同じです（タブ1〜7）。
   - Motor # を変えると、転送先のノードも切り替わります。
   - Write CAL や Write ULIM は、ノードの id と Motor # が一致しないと書き込みません。
6. `hall_live.py`：接続方法で `Head (RS-485)` を選び、node に ID を入れて Connect します。上の行に、電圧と電流がリアルタイムで表示されます。

## 仕組み

```
PC ──WiFi TCP 5000──> ヘッド ──RS-485 CALX_REQ（1行, seq）──> ノード cal_cmd()
PC <─テキスト + "t,S1,S2,u,mV,mA"─ ヘッド <─CALX_DATA（返事の行 + 最大 23 サンプル）─ ノード
```

- **ポーリング：** ヘッドはストリーム中は 10 ms ごと、それ以外は 50 ms ごとにノードへデータを取りに行きます。返事に「まだある」の印が付いていれば、すぐ次を取りに行きます。
  - 1 kHz のサンプルは 10 ms あたり 10 個なので、1回の返事に収まります。
- **再送：** 返事が来なければ、ヘッドは同じ seq でもう一度送ります（最大 3 回）。
  - ノードは同じ seq を2回目に受けたとき、前と同じ返事を再送します。
  - そのため、コマンドが2回実行されたり、データが抜けたりすることはありません。
  - PC 上のシミュレーションで、バスのフレームを 1/7 と 1/11 の割合で落としても、2002 サンプルが欠けも重複もなく届くことを確認しました。
- **時刻：** ノードは、ビーコン（20 Hz）による時刻同期を使って、サンプルの時刻をヘッド時刻に直して送ります。ヘッドは同じヘッド時刻で記録した INA226 の値を補間して付けます。
  - 同期がまだ取れていないとき（ノード起動直後の約 2 秒）は、到着時刻で合わせます（±20 ms 程度）。その場合は `INFO head: node … not time-synced` と表示されます。
- **INA226：** ブリッジに PC がつながっている間は高速設定（平均 1 回・変換 1.1 ms）にし、2 ms ごとに読みます。切断すると元の設定（AVG）に戻します。
  - 電流の分解能は 1.25 mA です。
  - 電圧・電流の時刻合わせは ±1〜2 ms 程度です（変換時間ぶん）。
- **安全：**
  - PC が切断すると、ヘッドがノードに `STOP` と `HALL 0` を送ります。
  - ヘッドから 0.5 秒ポーリングが来なければ、ノードは自分で駆動とストリームを止めます。
  - ヘッドの過電流トリップは今までどおり働きます。
  - ノードが走行中（WAIT / RUN）のときは、駆動・ストリームのコマンドを断ります。
- **今までの機能への影響：** ブリッジは、通常の要求（discover・param・arm・go・dump・REPORT 取り）が空いているときだけバスを使います。ブリッジにつないだままでも、ポート 5555 の `discover`・`peek`・`param`・`arm` が動くことを確認しました。

## ブリッジ専用コマンド（ポート 5000。ほかの行はすべてノードへ転送）

| コマンド | 内容 |
|---|---|
| `NODE <id>` | 転送先のノードを選びます（NVS `calnode` に保存）。前のノードには STOP / HALL 0 を送ります |
| `HEAD POWER 0\|1` | ノードへの給電（ロードスイッチ）を切り替えます |
| `HEAD INFO` | fw、給電、INA226 の状態、電圧・電流、転送先、受け取ったサンプル数を表示します |

## 電流の読み方（DRV8833 スローディケイ）

ノードはスローディケイで駆動しています。PWM が OFF の間、コイル電流はブリッジの中を回るので、電源からは流れません。そのため、次の関係になります。

```
I_電源 − I_待機 = duty × I_コイル          duty = MIN_DUTY + |u|·(1 − MIN_DUTY)
I_コイル ≈ duty × V / R    （止まっているとき）  →  I_電源 ≈ I_待機 + V·duty² / R
```

- **磁場（Hall の漏れ）が比例するのは I_コイル** です。GUI は MIN_DUTY（ノードの STATUS から取って記録に残す）を使って I_コイル を計算し、「k per coil A」を出します。
- 止まっているときの電源電流は u に対して**ほぼ 2 乗**で増えます。そのため、タブ5のフィットは、ステップが 3 点以上あれば 2 次式にしました。
- フィンが動いているときは逆起電力で I_コイル が減ります。タブ7で「k per u」と「k per 測った電流」のばらつきを比べると、どちらが Hall の実際の変化に合っているかが分かります。

## 検証の範囲

PC 上で、ヘッドとノードのファームを別々のプロセスとしてビルドし、RS-485 を UNIX ソケットで模擬して動かしました。INA226 も、ノードの duty から電流を作る模型にしました。確認したことは次のとおりです。
- ストリーミング（1 kHz、フレームを落としても欠けなし）
- コマンドの往復
- 電圧・電流が付くことと、その時刻
- PC 切断・ヘッド停止での安全停止
- 通常のゲートウェイコマンドとの同居
- GUI のタブ5（自動の電流測定 → 2 次式フィット）・タブ6（電流と k/A）・タブ1 の撮影（CSV に V/I の列）・hall_live

`node_calwifi`（ノード単体の WiFi）も、今までどおり動くことを確認しました。

**ESP32 実機用のツールチェーンでのビルドと、実機での動作はまだ確認していません。** 特に次の点を見てください。
- ヘッドの I2C の速さ：2 ms ごとに 2 レジスタを読みます。
- RS-485 の応答時間：返事は最大 250 B で、約 2.7 ms かかります。
- 確認には、ポート 5000 の `HEAD INFO`（samples が 1 秒に約 1000 増える）と、ポート 5555 の `bus`（timeouts が増え続けない）を使ってください。
